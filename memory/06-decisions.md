# 06. Архитектурные решения

Статус: **Фаза 1: утверждено** (09.10.2026). Формат: что выбрано →
альтернативы → почему. Раздел А — решения пользователя (не пересматриваются
без него), раздел Б — производные решения архитектора.

## А. Подтверждено пользователем

1. **`device_id`** — UUID v4, генерирует Android при первом запуске, хранит в
   DataStore, шлёт `X-Device-Id`; сервер хранит в `customers.device_id`.
   **Ограничение:** переживает выход и очистку кэша, **не переживает**
   «Очистить данные» и переустановку — появляется новый клиент без истории.
   Чтобы это было правдой и в обратную сторону, файл DataStore с
   идентификатором исключён из Android Auto Backup (иначе восстановление на
   втором телефоне дало бы двум устройствам один `device_id`).
2. **Схема БД** — ровно шесть таблиц с именами столбцов пользователя
   (`02-database.md`). `image_url` добавлен с его согласия. Таблиц
   `categories`, `translations`, `devices` нет.
3. **Статусы** `NEW → IN_PROGRESS → READY → PICKED_UP` + `CANCELLED`, только
   вперёд. Отмена: клиент — из `NEW`; бариста — из `NEW`/`IN_PROGRESS`.
4. **Один активный заказ** на клиента (NEW/IN_PROGRESS/READY).
5. **Бариста** — один общий пароль кофейни в `.env`; панель `X-Device-Id` не шлёт.
6. **Оплата при получении** — платёжных сущностей нет.
7. **Push нет**: Android поллит раз в 5 с, на `READY` — локальное in-app
   уведомление; панель тоже поллит.
8. **Бариста**: видит заказы и `code`, меняет статус, управляет стоп-листом.
9. **i18n en/ru/hy** — для UI Android и панели; контент меню — только английский.
10. **Стек**: Python 3.12 + FastAPI + SQLAlchemy 2 + PyMySQL + Alembic +
    pytest; React + Vite; MySQL 8; Docker Compose; Terraform (GCP); GitHub Actions.
11. **GCP-аккаунта нет**: Terraform пишется целиком, проверяется только
    `fmt`/`validate`; `apply` — позже.
12. Разбивка репозиториев: backend + панель + CI/CD здесь, Docker + Terraform
    + nginx — в `BrewQ_image`.
13. Конверт ошибок `{error:{code,message,details}}`.

## Б. Решения архитектора

### Б1. Хранение времени — UTC `DATETIME(6)`, сутки — по Еревану
- Альтернативы: локальное ереванское время в БД; `TIMESTAMP`.
- Почему: UTC — однозначно и привычно для логов/API; `TIMESTAMP` зависит от
  `time_zone` сессии и запрещён в функциональном индексе; `(6)` — порядок
  событий внутри секунды. Ереванские сутки получаются сдвигом +4 ч
  (Asia/Yerevan без DST с 2012), сдвиг живёт в одном модуле и в одном
  индексе, юнит-тест сверяет его с tzdata.

### Б2. `orders.code` — MAX за сутки + функциональный UNIQUE + повтор транзакции
- Альтернативы: таблица-счётчик (запрещено — новых таблиц нет); `GET_LOCK`
  (сессионная блокировка теряется/зависает при пуле соединений);
  `SELECT … FOR UPDATE` по диапазону (gap-локи совместимы друг с другом и дают
  deadlock'и на вставке — ретрай нужен всё равно); generated column
  `business_day` (новый столбец — нарушение схемы пользователя).
- Почему: `UNIQUE ((DATE(created_at + INTERVAL 4 HOUR)), code)` (MySQL 8.0.13+
  функциональные key parts, UNIQUE допускается) — гарантия на уровне БД без
  новых столбцов; гонка разрешается дубликатом ключа и повтором транзакции
  (≤3). Для одной кофейни конкуренция мизерная, код простой и проверяемый.
- Не проверено на живой MySQL на Фазе 1 (образа нет локально) — критерий
  Backend-задачи: миграция создаёт индекс, дубликат даёт 1062, `EXPLAIN`
  показывает индекс.

### Б3. После `A-999` — `409 DAILY_ORDER_LIMIT_REACHED`
- Альтернативы: `A-1000` (ломает формат), переход на `B-001` (новая
  семантика буквы, которую никто не просил), начать заново с `A-001`
  (коллизия с живыми заказами дня).
- Почему: 999 заказов в сутки для одной кофейни нереальны; честная ошибка
  проще и безопаснее молчаливой схемы. Клиент показывает «Сегодня заказы
  больше не принимаются».

### Б4. Перечисления — `VARCHAR` + именованный `CHECK`, не `ENUM`
- Почему: Alembic/SQLAlchemy (`native_enum=False, create_constraint=True`)
  делает это штатно; изменение набора — drop/add constraint без перестройки
  таблицы; нет ловушек `ENUM` (сортировка по индексу значения, пустая строка
  на невалидном значении при нестрогом режиме). Значения проверяются и в
  БД, и в Pydantic.

### Б5. FK — `RESTRICT`, позиции меню не удаляются
- Почему: в `order_items` нет снапшота имени, история держится на
  `menu_items`. Удаление = стоп-лист. `cart_items.customer_id` — `CASCADE`
  (клиентов никто не удаляет, но если удалят — корзина не нужна).

### Б6. Размер допустим только при наличии цены
- `price_for(item, size)`; нет цены → `SIZE_NOT_OFFERED` на добавлении,
  `reason:"size_not_offered"` при оформлении (если цену убрали сидом позже).

### Б7. Корзина на сервере, оформление — одна транзакция
- Порядок шагов — `02-database.md`. Проблемные строки возвращаются **все
  сразу**, корзина при ошибке не меняется, при успехе очищается в той же
  транзакции. Блокировка строки `customers` сериализует двойное нажатие.

### Б8. Переход статуса — compare-and-set `UPDATE … WHERE status = :from`
- Почему: гонка «клиент отменяет / бариста начинает» решается без
  блокировок и без шанса двух переходов из одного состояния; явный `to` в
  запросе делает повторное нажатие безопасным.

### Б9. Аутентификация баристы — `POST /login` → JWT HS256 (12 ч)
- Альтернативы: Bearer с самим паролем (пароль лежал бы в браузере и летел
  бы каждые 5 с, не истекает, светится в логах прокси); серверные сессии
  (нужна таблица); cookie-сессия (нужна CSRF-защита).
- Почему: без таблиц, без состояния, токен истекает к концу смены; claim
  `pwv` = HMAC(secret, password) гасит все токены при смене пароля;
  перебор режет nginx (5/мин). Хранение токена в `localStorage`: планшет у
  стойки, браузер выгружает фоновые вкладки, `sessionStorage` заставлял бы
  вводить пароль посреди смены; при XSS оба хранилища одинаково уязвимы,
  защита — строгий CSP.

### Б10. Чужой заказ → `404`, а не `403`
- Почему: не раскрываем, существует ли заказ с таким `id`.

### Б11. Картинки — файлы в репозитории, раздаёт nginx
- `app/media/menu/*` → `/srv/brewq/app/media/` → `location /media/`. В БД —
  относительный путь. Загрузки через API нет (меню = код). В dev FastAPI
  монтирует `StaticFiles` при `SERVE_MEDIA=true`. Новая версия картинки —
  новое имя файла (кэш `expires 7d`).

### Б12. Меню как код (`seed/menu.json`)
- Альтернатива: CRUD меню в панели — не просили, лишняя поверхность.
- Сид — upsert по `name`, не трогает `is_available`, ничего не удаляет.

### Б13. Панель — статика с диска, не контейнер
- Альтернатива из черновика: web-контейнер на `127.0.0.1:8082`.
- Почему (как в Miasin): правка панели = распаковка архива и атомарный
  симлинк, откат без пайплайна, на один контейнер и один порт меньше.

### Б14. Docker-файлы из `BrewQ_image` попадают на сервер через деплой этого репозитория
- Альтернатива: Terraform кладёт `docker/` на VM (`null_resource`, как
  конфиг nginx), деплой шлёт только код.
- Почему отвергнута: правка Dockerfile требовала бы `terraform apply` с
  ноутбука, а CI не мог бы собрать реальный образ. Сейчас CI клонирует
  публичный `BrewQ_image` на `BREWQ_IMAGE_REF`, собирает и проверяет тот же
  образ, что едет на сервер. Цена — ссылка на чужой репозиторий в CI;
  закрепление `BREWQ_IMAGE_REF` делает её управляемой.

### Б15. `device_id` не секрет
- Кто знает чужой UUID, видит чужие заказы и может отменить чужой `NEW`.
  Принято: данных о платежах нет, имя необязательно, UUID v4 не угадать
  перебором. Массовое создание клиентов случайными UUID ограничено
  `limit_req` nginx. Усиление (подписанный токен устройства) — отдельной
  задачей, если появится чувствительное содержимое.

### Б16. Кто сменил статус — не хранится
- Столбца в `order_events` нет (схема пользователя). Отмену клиентом и
  баристой в истории не различить; если понадобится — вопрос пользователю о
  новом столбце.

## В. Решения реализации B1 (09.10.2026)

### В1. `requirements.txt` — только runtime, тестовые — в `requirements-dev.txt`
- Почему: Dockerfile (`BrewQ_image`) собирает wheel'ы из `requirements.txt`;
  pytest/ruff в образе не нужны. CI и разработчик ставят
  `requirements-dev.txt` (он включает `-r requirements.txt`). Отклонение от
  формулировки плана («dev: pytest, httpx, ruff» в том же файле); задача D3 должна
  вызывать `pip install -r requirements-dev.txt`.

### В2. Тест-клиент — `httpx2`, а не `httpx`
- Starlette 1.7 помечает `httpx` для `starlette.testclient` устаревшим и просит
  `httpx2`; пин `httpx2==2.13.1`.

### В3. Пины на момент 09.10.2026
- fastapi 0.143.0, uvicorn 0.54.0, SQLAlchemy 2.1.4, PyMySQL 1.2.3 (+rsa), alembic
  1.20.0, pydantic-settings 2.15.0, PyJWT 2.15.1, tzdata 2026.5; dev: pytest 9.1.1,
  httpx2 2.13.1, ruff 0.16.10. Обновление — осознанное, через прогон тестов.

### В4. Настройки: пустое значение = значение по умолчанию
- `env_ignore_empty=True`: строка `KEY=` из скопированного `.env.example` не ломает
  разбор `bool`/`int`. Если задан `BARISTA_PASSWORD`, то `BARISTA_TOKEN_SECRET`
  обязан быть не короче 32 символов (старт падает сразу, а не при первом входе).
  `ENABLE_DOCS` (по умолчанию `false`) включает `/api/docs` и `/api/openapi.json`;
  иначе nginx отдавал бы документацию наружу. `LOG_LEVEL` принимается без учёта
  регистра (`INFO`/`info`/`Debug`) и нормализуется в верхний: bootstrap и compose пишут `INFO`.

### В5. Фреймворковые HTTP-ошибки без кода в контракте
- 404 → `NOT_FOUND`, 405 → `METHOD_NOT_ALLOWED`, 5xx → `INTERNAL_ERROR`, остальные
  4xx от Starlette → `HTTP_ERROR` (кода нет в `03-api.md`; клиенты по правилу
  «неизвестный код → UNKNOWN» это переживут). Некорректный JSON и лишние поля →
  `400 VALIDATION_ERROR`.

### В6. Интеграционные тесты стирают схему только в базе `*_test`
- Защита от случайного удаления базы разработки: фикстура отказывается работать,
  если имя базы не заканчивается на `_test`.

### В7. Картинки меню — сгенерированные SVG-заглушки
- 12 файлов `app/media/menu/<name>.svg` (иконка чашки/пирога на цветном фоне,
  без текста и шрифтов). В `seed/menu.json` пути вида `/media/menu/latte.svg`;
  nginx отдаёт `image/svg+xml` штатно. Замена на настоящие фото — новое имя файла
  и правка `seed/menu.json` (кэш `expires 7d`). Клиенты должны уметь рисовать SVG
  (Coil на Android — через `SvgDecoder`; уточнить в `BrewQ_android`).
- Цены в `seed/menu.json` — заглушки до ответа пользователя (по плану).

## Г. Решения реализации B2/B3 (09.10.2026)

### Г1. Регистрозависимые `CHECK`, формат `code` в БД
- `category/size/status/from_status/to_status/code` — `ascii` + `ascii_bin`;
  `ck_orders_code` = `REGEXP '^A-[0-9]{3}$' AND code <> 'A-000'`. Решение оркестратора,
  `code` добавлен к списку (иначе `REGEXP` нечувствителен к регистру: `a-001` прошёл бы).
  Миграция `0001` правилась на месте. Подробно — `02-database.md`.
- Реализация: `AsciiBinEnum` в `db/types.py` (у `Enum` SQLAlchemy 2.1 параметр
  `collation` молча теряется и нет `charset`).

### Г2. Повторы оформления: 15 попыток, а не 3
- Измерено: 10 одновременных оформлений дают повторы до 9-й попытки (за раунд
  выигрывает один). Лимит 3 из первоначального проекта не выдерживает требуемого
  критерия «10 параллельных → коды подряд». Теперь 15 + джиттер 0–30 мс
  (`services/checkout.py`). Альтернатива (`GET_LOCK` вокруг выдачи кода) отвергнута
  по-прежнему — см. Б2.

### Г3. Сериализация корзины и оформления — блокировка строки клиента
- Добавление/правка/удаление строк корзины и оформление берут
  `SELECT ... FOR UPDATE` по `customers`; чтение строки корзины — блокирующее.
  Без этого `REPEATABLE READ` + `INSERT ... ON DUPLICATE KEY` давали бы дубликаты
  или превышение лимита 20 при параллельных запросах (тест на 8 параллельных
  добавлений: ровно 6 успехов из 8 при qty 3 и лимите 20).
- Лимит 20 проверяется в приложении под блокировкой (`CART_QTY_LIMIT_EXCEEDED` с
  `current`), а не `CHECK`-ошибкой БД; `CHECK` остаётся страховкой.

### Г4. Слои и модули
- `services/`: `customer`, `menu`, `cart`, `checkout`, `orders` (клиентские чтения и
  отмена), `order_views` (read-модели `OrderView`), `order_transitions`
  (`apply_transition` — единственное место смены статуса: compare-and-set + событие в
  одной транзакции), `barista_auth`, `barista_orders`, `errors` (фабрики `AppError`).
- Сервисы возвращают `dataclass`-представления, Pydantic-схемы строятся в роутере
  (`Schema.model_validate(view)`); FastAPI не получает dataclass напрямую, иначе
  потерял бы вычисляемые `can_cancel`/`allowed_transitions`.
- `db/uow.py` — `unit_of_work(session)`: commit при успехе, rollback при любом
  исключении; сервис владеет транзакцией.
- Время в ответах — `UtcTimestamp`: всегда шесть знаков дроби и `Z`.

### Г5. Токен баристы (реализация Б9)
- `core/security.py`: PyJWT, `algorithms=["HS256"]` (`none`, HS384/512 отвергаются),
  `require` = `exp, iat, sub, pwv`; срок проверяется по `Clock` приложения
  (`verify_exp=False` у библиотеки), поэтому тесты двигают время. Сравнение пароля и
  `pwv` — `hmac.compare_digest` по байтам UTF-8 (строка с не-ASCII вызвала бы
  `TypeError`). Пустой `BARISTA_PASSWORD`/секрет = доступ баристы выключен: вход
  всегда `BARISTA_INVALID_PASSWORD`, токены не принимаются.
- Порядок проверок на `/api/barista/*`: токен проверяется **до** тела запроса
  (плохой токен + плохое тело = 401).
- Клиентские эндпоинты Bearer-токен не принимают (нужен `X-Device-Id`).

### Г6. Отклонения/уточнения контракта `03-api.md`
- Добавлен `HTTP_ERROR`; `unit_price_amd`/`line_total_amd` строки корзины могут быть
  `null` при `size_not_offered`; время всегда с шестью знаками дроби; `to: "NEW"` и
  неизвестный `scope`/нечисловой id — `400 VALIDATION_ERROR`. Полный список — в
  отчёте задачи и в самом `03-api.md`.

## Д. Редизайн панели R5 и веб-гигиена R7 (10.10.2026)

### Д1. Шрифт панели — Sora (Latin) + Noto (кириллица, армянский), все грани с одним `font-weight`
- Альтернативы: Google Fonts / CDN (запрещено CSP `'self'`); оставить Noto Sans.
- Почему: бренд-шрифт редизайна Sora (OFL) идёт из npm `@fontsource-variable/sora`
  и лежит в `dist/assets`; у Sora нет кириллицы и армянского, их закрывает Noto по
  `unicode-range` в том же семействе `BrewQ Sans`. Все четыре грани обязаны
  иметь одинаковый `font-weight` (`100 800`), иначе браузер выбирает «лучшую по
  весу» грань и `unicode-range` остальных не доходит до дела (найдено проверкой).

### Д2. Контраст: отклонения от токенов плана
- Белый на #C67C4E — 3,4:1: подпись на акценте — только крупная жирная
  (кнопки 19 px/700) или тёмная `--accent-ink-small` #1F1F1F; акцентный текст на
  фоне — `--accent-strong`. Светлая `--text-muted` #666666 (план: #6B6B6B) и
  `--status-new` #8C512C — иначе пилюля статуса на кремовом фоне ниже 4,5:1.
  Решено тестом `styles/contrast.test.ts` (разбирает `tokens.css`); токены Android
  стоит сверить с этим (там тот же #6B6B6B).

### Д3. Политика конфиденциальности — статические страницы, отдельные входы Vite
- Альтернативы: файлы в `public/` (нет доступа к хэшированному CSS и шрифтам
  без CDN или inline-стилей); раздел внутри SPA (нужен JS, и маршрут пришлось бы
  делать публичным в `RequireAuth`).
- Почему: три HTML-входа (`privacy.html`, `.ru.html`, `.hy.html`) без JS получают
  CSS и шрифты бандла; отдельные файлы нужны ещё и потому, что кириллица
  разрешена только в `ru`-файлах (`ci/check-cyrillic.sh`). nginx отдаёт их как
  обычные файлы, менять `BrewQ_image` не нужно. Текст не обещает того, чего нет:
  автоудаления данных в backend нет, срок хранения — `TODO(user)`.

### Д4. Заголовок вкладки собирает один компонент
- `ui/DocumentTitle` (все маршруты) читает путь, язык и число непросмотренных
  заказов из `ui/titleBadge`; `NewOrderWatcher` заголовок больше не пишет, а `i18n`
  только ставит `<html lang>`. Иначе два автора перебивали бы друг друга.

### Д5. Координаты кофейни живут в Android, API не менялся (R4)
- Альтернативы: `GET /api/shop` + таблица/конфиг на сервере; координаты в
  настройках панели.
- Почему: схема БД и контракт API зафиксированы пользователем; карта нужна одному
  клиенту, а позиция кофейни меняется раз в жизни. Android берёт её из Gradle-свойств
  `brewq.shopLatitude` / `brewq.shopLongitude` (`BuildConfig`). За интерфейсом

### Д6. Android-релиз — AAB для Google Play, не APK; в CI не входит (10.10.2026)
- Решение пользователя после R4: нативная MapLibre под 4 ABI сделала универсальный
  release-APK 44 МБ; в Google Play публикуется Android App Bundle
  (`bundleRelease`, 20,2 МБ; устройство получает одну ABI, ≈ 6,2 МБ загрузки на
  arm64-v8a, замер bundletool). Универсальный APK (`assembleRelease`) — только
  для ручной раздачи.
- `.github/workflows/ci-cd.yml` Android не собирает (только backend, панель,
  деплой), поэтому переключать в CI нечего; добавлять сборку и секреты подписи
  без просьбы не стали. Если понадобится: job с `./gradlew bundleRelease -P…` и
  загрузкой `app-release.aab` как артефакта; upload-ключ — только секретами
  репозитория (`keystore.properties` создаётся в job, в git его нет).
- Детали, защита `preReleaseBuild`, подпись и размеры по ABI —
  `BrewQ_android/memory/03-decisions.md` (решение 43) и `04-toolchain.md`.

### Д7. Позиция пользователя уходит на публичный сервис маршрутов (10.10.2026)
- Android рисует маршрут до кофейни и показывает «км · мин» (`BrewQ_android`, решение
  45): запрос идёт на публичный OSRM от FOSSGIS (`routing.openstreetmap.de`, без
  ключа). Поэтому прежняя формулировка политики «позиция никогда не отправляется ни
  на наш сервер, ни кому-либо ещё» стала неверной: на сервис маршрутов уходят позиция
  пользователя, позиция кофейни и IP (без `device_id` и имени); запросы редкие
  (сдвиг больше 50 м или смена режима, не чаще раза в 10 с, только на экране READY с
  разрешением). Страницы `privacy.html` / `privacy.ru.html` / `privacy.hy.html`
  обновлены (раздел «Ваше местоположение» и новый пункт «Третьи стороны»);
  `TODO(user)`-метки не тронуты. Бэкенд и API не менялись.
- Риск: бесплатный общий сервис без SLA и с политикой честного использования; при росте
  нагрузки нужен свой OSRM (меняется одним Gradle-свойством `brewq.routingBaseUrl`).
